Hello! I'd like to start on a new local-first application for tracking what folk tunes I've learned to play, would like to play, or have just recorded somewhere sometime. It'll be something between a todo list, a spaced-repetition/flashcard app, a cloude file store, and a music player. The backend will be pretty minimal, with almost all the code in a typscript+svelte PWA. It should work offline, and use the backend purely to deliver the app, to sync user state, provide file storage, and proxy/download data from third-party integrations. TBH we might not need a backend yet at all yet, depending on how we set things up.

The app should mainly consist of a list of "pieces", although that is an internal name only. In the UI a piece will be displayed as a "Session", "Set", "Tune", or "Part" (and that category will be changable with just a dropdown in the "Edit" modal). The user can easily add a new piece by pressing a (+) circle button in the lower-left corner on mobile, or a wider "Add +" button above the list on desktop. Each tune can be a minimal card with the usual kind of title, remove, edit, etc buttons for a "list of things" application. There should also be options for sorting/filtering the list by the attributes pieces have, and a search bar for finding up pieces by title (or later by more complicated text matchnig). Title and description are optional, as are pretty much all attributes and tags. Tags themselves can be arbitrary, the user gets to write up whatever new tag they want. The UI for managing tags should suggest and filter existing tags when the user types something in, but if they type something new they can always choose it as the tag. For example, "Irish", "Scottish", "Reel", "Jig", "Hornpipe", "Difficult", "Easy" etc could all be tags. Pieces should also have some metadata like "created at" and "modified at", and a favorited status with a little ★/☆ button.

One important attribute (which could just be a tag but may want some special handling) is a skill rating. Basically just a "out of 5 where 1 is never played and 5 is amazing" slider.

Now for some of the more interesting/unique features. First, pieces can have any number of audio recordings associated with them, which the user can add/remove/reorder/trim. The audio recordings can certainly be uploaded (being stored by the backend as some sort of asset, seperately from the synced local-first user state). But also recordings should be very easy to add from external 3rd-party sources such as YouTube, Google Recordings, Spotify, and Google Drive. This is something the backend might be needed to support. We could do some playback client-side direct from those sources maybe? But having access to the Google APIs and `yt-dlp` behind the scenes could be helpful, to convert into native audio files. If a source can't be played-back directly (eg spotify, or early on before all features are implemented) it should just open as a link. Regardless the original source of a recording should be known, and the UI might have some custom decoration depending.

Some recordings might not be audio. For example linking to thesession.org or folkfriend.app might be presented in the same UI. But those particular integrations should provide a ton of custom behavior. Linking to the thesession.org in particular should populate all kinds of data, for example providing sets the tunes might be part of (although not storing them as actual "Set" pieces in the user state unless asked). When adding a new tune, filling out the title might actually search thesession.org for the tune to populate from (including a few default tags like "Jig", "Reel", etc) if a search button next to the title is pressed. Similarly it the options to import recordings should be prominently displayed until at least one recording is present. And if a recording is uploaded with no title, maybe we can add an option for jigripper.com to identify it.

One other feature, there should be many-to-many associtations between pieces. Generally like session<->set<->tune<->part but that doesn't need to be enforced. Regardless these associations are created either by adding to a piece (shown as "Add Set" for Session, "Add Tune" for Set, etc) or by splitting a piece (shown as "Split Part" for tunes, "Split Tune" for set, etc). This can be done with entirely blank pieces, but the main use-case will be to select some part of the main recording to be associated with that new piece. The asset/source behind the scenes should be the same, just trimmed differently.

There should also be a way to merge duplicate pieces. Either automatically if linked to thessession (with a confirmation popup). Or manually.

Pieces should also have a prominent button to mark "Practiced". Each should keep a log of when it was practiced, and display the most recent time and date (if any). Later we might add plots and histograms and stuff. This can also tie into an additional flash-card feature: a "Shuffle" button (just an icon circle next to the add circle mobile) should open a random tune with buttons at the bottom for "Practiced ->" and "Skip ->", and the skill slider just above for adjustment. A little gear at the top might allow customization of how tunes are picked. I'd be interested in "Age Temperature", "Skill Temperature", and "Favorite Temperature" sliders which when high make the sorting more random and when low prioritize tunes played less recently, less skillfully, and tunes played more times and/or marked as favorites respectivly. The shuffle doesn't actually pick the list up front, we'll just keep track of which tunes were already shown since the shuffle view was opened, and pick from the remainder with probability determined by the factors and temperatures on each "Practiced/Skipped". By default only tunes should be included, but the gear should also provide checkboxes for parts/sets/sessions.

Under the hood, I imagine the app itself will be entirely static, servable from a CDN. As a PWA it will have a service worker and some auto-update behind the scenes when a new version is deployed to _wherever_ (probably cloudflare via cloudflare pages). If we add integrations with backend support, that might need me to setup on my VPS. TBH it could be serverless instead? I'm just nervous to tie it to cloudflare completely, I'd only do serverless if we could be agnostic somehow. For the user state, I'm thinking about using either Automerge (with an Automerge Repo handling cross-device sync) or Evolu.dev. Any opinions? To start with we could use the public relays, and rely entirely on third-party integrations for recordings. Google Drive and Google Recorder (see https://github.com/dylantmoore/google-recorder-cli maybe?) are the priority for audio files, and thesession.org (https://thesession.org/api) for everything else. We should do a spike early on to establish if for integration CORS reasons we should get the backend setup sooner or put it off for later.

I think that is everything for now. Any questions/thoughts? Anything I can help hash out? The goal right now is to author a detailed PLAN.md for us to follow going forward.
